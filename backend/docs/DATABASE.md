# Database

The POS backend uses the shared Cloudflare D1 database `afika` bound to the
Worker as `DB_BINDING` (default `afika`). Migrations live in
`backend/api/migrations` and are applied with Wrangler.

| Migration | Contents |
| --- | --- |
| `0001_wallet_settings.sql` | Legacy wallet settings. |
| `0002_pos_payments.sql` | `pos_payments` checkout links. |
| `0003_pos_schema.sql` | All server-side POS tables. |
| `0004_pos_payment_sale_link.sql` | `pos_payments.sale_id`, `business_id` + indexes. |

## Conventions

| Concern | Rule |
| --- | --- |
| Ids | 128-bit random hex `TEXT`, generated by `posstore.NewID()`. Not autoincrement, so a whole sale can be written in one batch. |
| Money | `INTEGER` ZAR cents everywhere. No float columns. |
| Crypto | `TEXT` decimal strings (`crypto_amount`, `crypto_rate`), so precision survives JSON/SQLite round-trips. |
| Time | `INTEGER` epoch milliseconds, UTC. Receipt formatting uses SAST (`+02:00`). |
| Scoping | Every POS row except `pos_guard`/`pos_idempotency` carries `business_id`. |
| Deletes | Categories are hard-deleted only while unused; products are soft-deleted with `active = 0`. Sales/refunds are never deleted. |
| Referential integrity | Foreign keys are declared and enforced by D1 (and by modernc SQLite in tests). |

### `pos_receipt_counters`

| Column | Type | Notes |
| --- | --- | --- |
| `business_id` | TEXT PK FK | |
| `next_no` | INTEGER | `CHECK (> 0)`; incremented atomically. |

Receipt numbers are allocated with:

```sql
INSERT INTO pos_receipt_counters (business_id, next_no)
VALUES (?, 2)
ON CONFLICT (business_id) DO UPDATE SET next_no = next_no + 1
RETURNING next_no - 1;
```

### `pos_idempotency`

| Column | Type | Notes |
| --- | --- | --- |
| `business_id` | TEXT | Part of the PK. |
| `idem_key` | TEXT | Part of the PK. |
| `scope` | TEXT | `sale` or `refund`. |
| `request_hash` | TEXT | Detects a reused key with a different request. |
| `response_json` | TEXT | Replayed verbatim on a hit. |
| `created_at` | INTEGER | |

`PRIMARY KEY (business_id, idem_key)` makes concurrent retries race on one row;
exactly one batch commits.

### `pos_guard`

Single-purpose helper table for `Writer.ExpectOne()`:

```sql
CREATE TABLE pos_guard (ok INTEGER NOT NULL CHECK (ok = 1));
```

It stays empty on success. A guarded statement that changed no rows inserts
`0`, fails the CHECK, and aborts the whole D1 batch. See `ARCHITECTURE.md`.

## App schema vs server schema

The app keeps its own SQLite database (`app/src/db/bootstrap.ts`). It is not a
copy of the server schema:

| App | Server |
| --- | --- |
| Integer autoincrement ids | Random hex TEXT ids |
| `crypto_amount`/`crypto_rate` are `REAL` | TEXT decimal strings |
| `business` is a single `id = 1` row | `pos_businesses` keyed by `owner_id` |
| `payment_requests` mirrors the local flow | `pos_payments` adds merchant, URL, expiry, sale link |
| No `business_id` (single merchant) | Every row is business-scoped |
| No idempotency table | `pos_idempotency` |

A sync layer would map app integer ids to server hex ids; see `OFFLINE_SYNC.md`.

## Constraints that encode business rules

- `pos_sales.refunded_total <= total` — refunds can never exceed the sale.
- `pos_sale_items.refunded_qty <= qty` — no over-refund per line.
- `pos_customers.loyalty_points >= 0` — points cannot go negative.
- `pos_products.stock >= 0` — stock cannot go negative.
- `pos_stock_movements.balance_after >= 0` — ledger agrees with stock.
- Status/type CHECKs keep the app's status vocabulary.

Business-level rules (void only when completed and unrefunded, refunds only
from completed sales, proportional loyalty reversal) are enforced in
`posservice`/`posdomain`; the database constraints are the last line of
defence.

## Migrations

```bash
cd backend/api
npx wrangler d1 migrations apply afika --local
npx wrangler d1 migrations apply afika --remote
```

`backend/scripts/test-database.sh` applies every worker's migrations to one
temporary local D1 database, then verifies tables, columns, constraints,
receipt-counter atomicity, and the `pos_guard` abort behaviour. Migrations must
not contain semicolons inside statements or comments, because the Go test
helpers split DDL on `;`.
